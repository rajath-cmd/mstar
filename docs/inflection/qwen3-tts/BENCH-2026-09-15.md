# M* vs vllm-omni — Qwen3-TTS batch latency/throughput, 2026-09-15

**Checkpoint:** `sft-cv-13l-14pv-ticr-1e-13l-fulldata_17946/checkpoint-final` (identical both arms) — the SFT checkpoint that ships the TFA head
**Hardware:** one B200 per arm — M* on GPU 0, vllm-omni on GPU 1, same host
**Harness:** `benchmark/inflection/tts_ab.py --mode batch --reps 5`
**Method:** same client, same 5-sentence corpus, same ladder. Arms **interleaved per
concurrency level**, so thermal drift and co-tenant noise hit both equally rather than
landing on whichever ran second. 5 rounds per level.

Raw data: `bench-2026-09-15-results.json`. Re-measured on `...-nospeed_22253` as well: every figure reproduced within noise, so the gap is architectural rather than checkpoint-specific. Plots are regenerated into `out/` (gitignored)
by rerunning the command below.

## Fairness gate

A faster server that emits *shorter audio* would win every derived metric while doing less
work, so mean audio duration is checked per level before any comparison is reported.

| conc | M* audio | vllm-omni audio | ratio |
|---:|---:|---:|---:|
| 1 | 4.94 s | 5.04 s | 0.981 |
| 4 | 5.24 s | 5.05 s | 1.038 |
| 8 | 4.95 s | 4.95 s | 0.999 |
| 16 | 5.03 s | 4.92 s | 1.024 |
| 32 | 5.13 s | 4.94 s | 1.038 |

All within ±15 %, and M* produces *slightly more* audio per request — so the results below
understate its advantage rather than flattering it.

| 1 | 344 ms | 1210 ms | **3.51×** | 0.083 | 0.256 | 12.5× | 3.9× | 3.21× |
| 4 | 597 ms | 1850 ms | **3.10×** | 0.135 | 0.427 | 21.3× | 6.7× | 3.15× |
| 8 | 715 ms | 3043 ms | **4.26×** | 0.155 | 0.681 | 32.7× | 9.0× | 3.61× |
| 16 | 932 ms | 5564 ms | **5.97×** | 0.192 | 1.190 | 48.7× | 11.3× | 4.33× |
| 32 | 1299 ms | 9571 ms | **7.37×** | 0.270 | 2.164 | 67.7× | 12.8× | 5.28× |

100 % success on both arms at every level.

**The advantage widens with load** — 2.9–3.6× at low concurrency, 6.9× at 32. The RTF
column is the operationally important one: **vllm-omni crosses RTF = 1 between 8 and 16
concurrent requests** (1.176 at 16, 2.179 at 32). Past that it generates slower than
realtime and a voice agent cannot keep up. M* is at 0.278 at 32 — roughly 3.6× faster than
realtime.

## What this measures, and what it does not

**Does:** total request latency and aggregate throughput on the non-streaming REST path —
what a batch or offline consumer feels.

**Does NOT:** time-to-first-audio. Neither REST path delivers a meaningful TTFA today.
M* flushes its data chunks at completion (first byte is a 44-byte WAV header at ~75 ms,
then all PCM at ~488 ms). vllm-omni **re-sends cumulatively** — each chunk repeats
everything before it (3840, 7680, 11520, … ; 9 MB for ~5 s of audio, in `pcm` as well as
`wav`). The harness detects that pattern and suppresses audio-derived metrics; before the
guard existed it computed a physically impossible **464× realtime** for vllm-omni.

**TTFA belongs to the WebSocket** — the path pipecat actually uses, and the one M* does not
have yet (Phase 2). Until then, no TTFA claim should be made from this harness in either
direction.

## Alignment (word-timestamp) parity: not yet

This checkpoint ships `pointer_head.pt`, and vllm-omni loads it
(`loaded AlignmentPointerHead`, `alignment capture enabled`). M* has no alignment head
at all, so with `timestamp_type: "word"` it returns `timestamp_info: null` where
vllm-omni returns real words and times.

That is legal under the REST contract — `null` is exactly what vllm-omni gives for a
headless checkpoint — which is why it is asserted in a **separate suite**
(`test/parity/test_alignment_parity.py`) rather than the REST one. Left in the REST
contract it would let M* return null forever and still report green, masking the gap this
program exists to close.

    REST parity        12 / 12   green, both servers
    Alignment parity    3 / 3    green on vllm-omni, RED on M*  <- Phase 3

Those three turn green without edits when Phase 3 lands.

**The benchmark above is unaffected.** It never sets `timestamp_type`, and vllm-omni only
registers alignment capture when a request asks for word timestamps — so neither arm pays
alignment cost, and the comparison stays like-for-like.

## Two defects found while measuring

1. **M* has no runaway audio cap.** One c=1 round produced **16.4 s** of audio for a
   sentence that normally yields ~2.9 s. vllm-omni bounds this text-proportionally
   (`_TTS_RUNAWAY_CAP_FPC = 5.5` frames/char, floor 256, ceiling 2048); `grep` finds no
   equivalent anywhere in M*. A **parity gap**, not merely a benchmarking nuisance — a
   degenerate generation is unbounded on M* today. Tracked for Phase 2.

2. **vllm-omni's REST streaming re-sends cumulatively** (above). Its WebSocket path is
   unaffected, which is presumably why this has gone unnoticed: pipecat uses the WebSocket.

## Reproduce

```bash
MSTAR_MODEL_PATH=<ckpt> GPUS=0 scripts/inflection/launch_mstar_qwen3_tts.sh 8100
MODEL=<ckpt> CUDA_VISIBLE_DEVICES=1 <vllm-omni>/scripts/inflection/launch_tts_ws_server.sh 8901

python -m benchmark.inflection.tts_ab \
  --mstar http://127.0.0.1:8100 --omni http://127.0.0.1:8901 \
  --concurrencies 1,4,8,16,32 --reps 5 --mode batch --out out/tts_ab_batch
```
